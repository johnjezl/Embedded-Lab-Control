# Connecting Claude Code agents

How to give a Claude Code session its own labctl identity, so that several
agents can share the lab without power-cycling or flashing a board another
agent is using.

## How it works

- The `labctl-mcp` service (HTTP, `127.0.0.1:8080` by default) runs with
  `auth.enabled: true`. Every request must carry
  `Authorization: Bearer <api_key>`.
- An API key belongs to one entry in `auth.users` in
  `/etc/labctl/config.yaml`. The server identifies the caller **from the
  key alone**: the agent never sends, or needs to know, its username.
- Each user is a separate **claimant**. When an agent claims a board
  (`claim_sbc`), mutating tools called by any *other* user on that board
  (power, `serial_send`, SDWire switching and updates, `flash_image`,
  `boot_test`, actuator and recovery tools, `remove_sbc`) are refused
  with `"error": "sbc_claimed"`.

So the rule is **one labctl user and key per agent**. Two agents sharing a
key are the same claimant, and their claims do not protect them from each
other.

These are **labctl** keys, generated by `labctl user generate-key`. They
are unrelated to Anthropic API keys.

(Over **stdio** instead, `claude mcp add labctl -- labctl mcp` on the lab
host, every Claude Code session starts its own `labctl mcp` process and
each process is already a separate claimant, without keys. But those
claims show up as `unnamed-…` unless the agent passes `agent_name`, the
server runs with your own permissions and database access, and it only
works on the lab host. This guide covers the HTTP service.)

What keys do *not* do:

- **Unclaimed boards are open to everyone.** Agents must claim before they
  touch a board (see [Agent instructions](#agent-instructions)).
- **The `labctl` CLI, web UI and REST API don't check claims** (except
  `remove`). An agent with a shell on the lab host can bypass claims by
  running `labctl power cycle ...`; tell agents to use MCP tools only.
- **Keys separate cooperating agents; they don't isolate them.** Agents
  running as the same Linux user can read each other's key files (and
  `~/.claude.json`). For isolation between people, use separate Linux
  accounts.
- **Restarting `labctl-mcp` releases every claim.** Claims belong to the
  server process; after a restart agents start unclaimed and must claim
  again. Restart when no agent is mid-operation.

## Prerequisites

- `labctl-mcp` is running (`systemctl is-active labctl-mcp`) with
  `auth.enabled: true` (`labctl -c /etc/labctl/config.yaml mcp --http 8080
  --check` prints `auth: required`; it checks the config, not the running
  service).
- You can edit `/etc/labctl/config.yaml` (root), and you are in the
  `labctl` group (to run the check above).
- Claude Code is installed on the machine the agent runs on. If that is
  not the lab host, forward the port first, e.g.
  `ssh -N -L 8080:127.0.0.1:8080 labhost`.

## Step 1: create the agent's labctl user

Both methods below start here. Pick a name for the agent: any unique
string you like, e.g. `fw-dev` or `ci-boottest`. It shows up in the
activity log and, by default, in claims.

```bash
NAME=fw-dev
KEY=~/.config/labctl/agents/$NAME.key
mkdir -p -m 700 ~/.config/labctl/agents
# Generates the key and prints the YAML entry to paste (nothing on failure):
(umask 077; labctl user generate-key > "$KEY") && [ -s "$KEY" ] &&
    printf -- '- username: %s\n  api_key: %s\n' "$NAME" "$(cat "$KEY")"
```

(If `labctl` isn't on your `PATH`, use `/opt/labctl/venv/bin/labctl`.)

Add the printed entry under `auth.users`, indented like the existing
users:

```bash
sudoedit /etc/labctl/config.yaml
```

```yaml
auth:
  enabled: true
  users:
    - username: labctl          # existing user
      ...
    - username: fw-dev          # new agent
      api_key: <key>
```

Agents don't need a `password_hash` (that is only for web UI logins).

Then check the file still loads:

```bash
labctl -c /etc/labctl/config.yaml mcp --http 8080 --check
```

**No restart is needed.** The server re-reads API keys from the config
file on every request, so the new key works on the agent's next call.
(Every other setting needs a restart, which releases all claims.) While the file doesn't load,
e.g. after saving a YAML mistake, **every** key is refused, which is why
`sudoedit` (it saves only when you quit) and the check above matter.

The key file in `~/.config/labctl/agents/` is used by the streamlined
method; the manual method copies the key into Claude Code's own config
instead.

## Method A: manual (`claude mcp add`)

Register the server in Claude Code, from the agent's project directory:

```bash
cd ~/projects/my-firmware
claude mcp add --transport http --scope local labctl http://127.0.0.1:8080/mcp \
  --header "Authorization: Bearer $(cat ~/.config/labctl/agents/fw-dev.key)"
```

Check it:

```bash
claude mcp list          # labctl: http://127.0.0.1:8080/mcp (HTTP) - ✔ Connected
claude mcp get labctl    # scope, URL and headers
```

A wrong or revoked key shows as failed to connect (the server answers
HTTP 401). Then start Claude Code in that directory as usual (`claude`);
`/mcp` inside the session shows the connection too.

Notes:

- `--scope local` (the default) stores the server, key included, in
  `~/.claude.json` for **this directory only**, for your Linux user.
  Every Claude Code session started in that directory uses the same key,
  i.e. is the same agent. Git worktrees of a repository share its entry,
  so they are one agent too; use Method B to run several.
- `--scope user` makes it apply to every directory; then all your sessions
  are one agent.
- Don't use `--scope project`: it writes the key into `.mcp.json`, which is
  meant to be committed.
- To change the key, `claude mcp remove labctl -s local` and add it again.

Method A suits one long-lived agent per directory.

## Method B: streamlined (`--mcp-config` + an environment variable)

One shared, secret-free config file for all agents; the key is picked at
launch. This lets several agents run in the **same** directory with
different identities, and starting a new agent is just step 1 plus a
launch command.

Create the shared file once, `~/.config/labctl/claude-mcp.json`:

```json
{
  "mcpServers": {
    "labctl": {
      "type": "http",
      "url": "http://127.0.0.1:8080/mcp",
      "headers": { "Authorization": "Bearer ${LABCTL_API_KEY}" }
    }
  }
}
```

Claude Code expands `${LABCTL_API_KEY}` from its environment when it loads
the file. Launch an agent with:

```bash
LABCTL_API_KEY=$(cat ~/.config/labctl/agents/fw-dev.key) \
  claude -n fw-dev --mcp-config ~/.config/labctl/claude-mcp.json
```

`-n` names the session (prompt box, `/resume` list, terminal title).
Any other `claude` options can follow, e.g. `-p "..."` for a scripted run.

To make this a single word, add a shell function to `~/.bashrc`:

```bash
# Start Claude Code as labctl agent NAME: labagent NAME [claude options...]
labagent() {
    local name=$1 key=~/.config/labctl/agents/$1.key
    if [ -z "$name" ] || [ ! -s "$key" ]; then
        echo "usage: labagent NAME [claude options]; no key at $key" >&2
        return 1
    fi
    shift
    LABCTL_API_KEY=$(cat "$key") claude -n "$name" \
        --mcp-config ~/.config/labctl/claude-mcp.json "$@"
}
```

```bash
labagent fw-dev                          # interactive
labagent ci-boottest -p "Run a 10x boot test on pi-5-1"
```

Notes:

- If `LABCTL_API_KEY` is unset, Claude Code sends the text
  `${LABCTL_API_KEY}` literally and the server refuses it (401); the
  function above refuses to start instead.
- If the directory also has a `labctl` server from `claude mcp add`
  (Method A), the `--mcp-config` one is used. Avoid mixing the two
  anyway, or add `--strict-mcp-config`, which ignores every MCP server
  not in `--mcp-config` (other servers you use included).
- The key is in the session's environment, so commands the agent runs can
  see it (`echo $LABCTL_API_KEY`). See the isolation note under
  [How it works](#how-it-works).

## Agent instructions

Identity only helps if agents claim boards. Put rules like these in the
agent's `CLAUDE.md`:

```markdown
## Lab hardware (labctl)
- Use the labctl MCP tools for all lab hardware. Never run the `labctl`
  CLI for power, serial, SDWire or flashing: it bypasses claims.
- Before touching a board, `claim_sbc` it (with a short `reason`; leave
  `agent_name` unset so the claim shows your labctl user). If it
  is claimed by someone else, wait or call `request_sbc_release`; never
  call `force_release_sbc` unless I ask.
- `release_sbc` as soon as you are done; `renew_sbc_claim` for long runs.
- Destructive tools return `confirmation_required` first: check the plan,
  then call again with the same arguments plus `confirm_token`.
```

## Checking an agent's identity

Ask the agent to claim a spare board, then:

```bash
labctl -c /etc/labctl/config.yaml activity tail
#   ... mcp-stdio:<process>:fw-dev  claim  test-board ...
labctl -c /etc/labctl/config.yaml claims list
#   test-board  held by fw-dev (...)
```

The name after the last `:` in the activity log comes from the key: if it
is another agent's name, the two share a key. `claims list` shows the
claim's `agent_name`, which is the username unless the agent passed its
own.

## Revoking or rotating a key

- **Revoke:** delete the user's entry from `auth.users` (`sudoedit`). It
  takes effect on the next request, without a restart. Delete
  `~/.config/labctl/agents/NAME.key`, and for Method A,
  `claude mcp remove labctl -s local` in that directory.
- **Rotate:** generate a new key into the key file, replace `api_key` in
  the config, and for Method A re-add the server.
