# Connecting Claude Code agents

How to give a Claude Code session its own labctl identity, so that several
agents can share the lab without power-cycling or flashing a board another
agent is using.

## How it works

- The `labctl-mcp` service (HTTP, `127.0.0.1:8080` by default) runs with
  `auth.enabled: true`. Every request must carry
  `Authorization: Bearer <api_key>`.
- An API key belongs to one entry in `auth.users` in
  `/etc/labctl/config.yaml`. The server identifies the caller **from the
  key alone**: the agent never sends, or needs to know, its username.
- Each user is a separate **claimant**. When an agent claims a board
  (`claim_sbc`), every MCP tool that operates or reconfigures that board
  is refused for every *other* user with `"error": "sbc_claimed"`: power,
  `serial_send`, SDWire, flashing, boot tests, relay bindings and
  recovery, and changes to its plugs, ports, addresses, SDWire assignment
  and bindings (full list in
  [MCP_SERVER.md](MCP_SERVER.md#claims-exclusive-access-coordination)).
  This needs `claims.enabled` (the default); with it `false`, nothing is
  enforced.
- Give agents `role: agent`. Over MCP, agents can't force-release another
  user's claim, only ask for it (`request_sbc_release`); users without a
  role are operators, who can. (The web REST API doesn't check roles yet.)

So the rule is **one labctl user and key per agent**. Two agents sharing a
key are the same claimant, and their claims do not protect them from each
other.

These are **labctl** keys, generated by `labctl user generate-key`. They
are unrelated to Anthropic API keys.

(Over **stdio** instead, `claude mcp add labctl --
/opt/labctl/venv/bin/labctl -c /etc/labctl/config.yaml mcp` on the lab
host, every Claude Code session starts its own `labctl mcp` process and
each process is already a separate claimant, without keys. But those
claims show up as `unnamed-…` unless the agent passes `agent_name`, the
server runs with your own permissions and database access, and it only
works on the lab host. This guide covers the HTTP service.)

What keys do *not* do:

- **Unclaimed boards are open to everyone**, unless you turn on
  `claims.require_claim` (recommended for several agents; see
  [Recommended settings](#recommended-settings)). Otherwise agents must
  remember to claim first (see [Agent instructions](#agent-instructions)).
- **Operators can still break a claim**: any user without `role: agent`
  over MCP, and people at the web dashboard or the CLI.
- **The `labctl` CLI acts as an operator.** It refuses to change a board
  someone else has claimed, but `--override-claim` overrides (logged), it
  doesn't know about claims made over MCP (not even the agent's own), and
  anyone with a shell on the lab host can edit the database directly.
- **The web UI and REST API don't check claims** (except deleting a
  board). The same API key also works on the web REST API (`X-API-Key`
  header) if `labctl-web` is running, where it can also force-release
  claims whatever its role. Tell agents to use MCP tools only.
- **Keys separate cooperating agents; they don't isolate them.** Agents
  running as the same Linux user can read each other's key files (and
  `~/.claude.json`). For isolation between people, use separate Linux
  accounts.
- **Restarting `labctl-mcp` drops claims.** A clean stop releases the
  claims made through that server process, and agents must claim again.
  If the process is killed instead (crash, stop timeout), its claims stay
  until they expire: they still belong to their agents (by username), who
  can keep using or release them, and block everyone else. A later clean
  stop doesn't release those older claims either. Restart when no agent
  is mid-operation.

## Prerequisites

- `labctl-mcp` is running (`systemctl is-active labctl-mcp`) with
  `auth.enabled: true` (`labctl -c /etc/labctl/config.yaml mcp --http 8080
  --check` prints `auth: required`; it checks the config, not the running
  service).
- You can edit `/etc/labctl/config.yaml` (root), and you are in the
  `labctl` group (to run the check above).
- Claude Code is installed on the machine the agent runs on. If that is
  not the lab host, forward the port first, e.g.
  `ssh -N -L 8080:127.0.0.1:8080 labhost`.

## Recommended settings

In `/etc/labctl/config.yaml` on the lab host, when several agents share
the lab:

```yaml
claims:
  require_claim: true    # MCP calls that change a board need its claim
```

Agents then get `"error": "claim_required"` instead of touching a board
they haven't claimed, so a forgotten `claim_sbc` can't hurt another
agent. Restart `labctl-mcp` to apply it. (The REST API doesn't check
claims yet.)

## Step 1: create the agent's labctl user

Both methods below start here. Pick a unique name for the agent:
letters, digits, `-` and `_`, starting with a letter, e.g. `fw-dev` or
`ci-boottest`. It shows up in the
activity log and, by default, in claims.

**On the machine the agent will run on**, create its key file:

```bash
NAME=fw-dev
KEY=~/.config/labctl/agents/$NAME.key
mkdir -p -m 700 ~/.config/labctl/agents
# Generates the key and prints the YAML entry to paste (nothing on
# failure). set -C: never overwrites an existing agent's key file.
(umask 077; set -C
 python3 -c 'import secrets; print(secrets.token_urlsafe(32))' > "$KEY") &&
    [ -s "$KEY" ] &&
    printf -- '- username: "%s"\n  api_key: "%s"\n  role: agent\n' \
        "$NAME" "$(cat "$KEY")"
```

The key is the same kind `labctl user generate-key` prints; `python3`
just means labctl needn't be installed there. If it fails with "cannot
overwrite existing file", that agent already has a key: pick another name,
or see [Rotate](#revoking-or-rotating-a-key). If it failed otherwise and
left an empty key file, delete that file before retrying.

**On the lab host**, add the printed entry under `auth.users`, indented
like the existing users:

```bash
sudoedit /etc/labctl/config.yaml
```

```yaml
auth:
  enabled: true
  users:
    - username: labctl          # existing user
      ...
    - username: "fw-dev"        # new agent
      api_key: "<key>"
      role: agent
```

Agents don't need a `password_hash` (that is only for web UI logins).
`role: agent` keeps them from force-releasing other agents' claims over
MCP.

If the service's own copy of the config exists
(`/var/lib/labctl/.config/labctl/config.yaml`), keep it identical:
`scripts/update.sh` refuses to update while the two differ. Copy as the
`labctl` user (which owns that file), not as root:

```bash
[ -f /var/lib/labctl/.config/labctl/config.yaml ] &&
    sudo -u labctl cp /etc/labctl/config.yaml /var/lib/labctl/.config/labctl/config.yaml
```

Do the same after every change to `auth.users` below (revoke, rotate).

Then check the file still loads (lab host):

```bash
labctl -c /etc/labctl/config.yaml mcp --http 8080 --check
```

**No restart is needed** for MCP. `labctl-mcp` re-reads API keys from the
config file on every request, so the new key works on the agent's next
call. (`labctl-web` reads keys only at startup: restart it if the key
should also work on the REST API.) Every other setting needs a restart,
which drops all claims. While the file doesn't load, e.g. after saving a
YAML mistake, **every** key is refused, which is why `sudoedit` (it saves
only when you quit) and the check above matter.

The key file is used by the streamlined method; the manual method copies
the key into Claude Code's own config instead. Both run on the agent's
machine; the identity checks further down run on the lab host.

## Method A: manual (`claude mcp add`)

Register the server in Claude Code, from the agent's project directory:

```bash
cd ~/projects/my-firmware
KEY=$(cat ~/.config/labctl/agents/fw-dev.key) && [ -n "$KEY" ] &&
  claude mcp add --transport http --scope local labctl http://127.0.0.1:8080/mcp \
    --header "Authorization: Bearer $KEY"
unset KEY
```

(The `[ -n "$KEY" ]` stops it from registering an empty key if the key
file is missing or empty.)

Check it:

```bash
claude mcp list          # labctl: http://127.0.0.1:8080/mcp (HTTP) - ✔ Connected
claude mcp get labctl    # scope, URL and headers
```

A wrong or revoked key shows as failed to connect (the server answers
HTTP 401). Then start Claude Code in that directory as usual (`claude`);
`/mcp` inside the session shows the connection too.

Notes:

- The key is on the `claude mcp add` command line, so other local users
  can see it in `ps` while the command runs. On a shared machine, use
  Method B instead.
- `--scope local` (the default) stores the server, key included, in
  `~/.claude.json` for **this directory only**, for your Linux user.
  Every Claude Code session started in that directory uses the same key,
  i.e. is the same agent. Git worktrees of a repository share its entry,
  so they are one agent too; use Method B to run several.
- `--scope user` makes it apply to every directory; then all your sessions
  are one agent.
- Don't use `--scope project`: it writes the key into `.mcp.json`, which is
  meant to be committed.
- To change the key, `claude mcp remove labctl -s local` and add it again.

Method A suits one long-lived agent per directory.

## Method B: streamlined (`--mcp-config` + an environment variable)

One shared, secret-free config file for all agents; the key is picked at
launch. This lets several agents run in the **same** directory with
different identities, and starting a new agent is just step 1 plus a
launch command.

Create the shared file once, `~/.config/labctl/claude-mcp.json`:

```json
{
  "mcpServers": {
    "labctl": {
      "type": "http",
      "url": "http://127.0.0.1:8080/mcp",
      "headers": { "Authorization": "Bearer ${LABCTL_API_KEY}" }
    }
  }
}
```

Claude Code expands `${LABCTL_API_KEY}` from its environment when it loads
the file. Launch an agent with:

```bash
LABCTL_API_KEY=$(cat ~/.config/labctl/agents/fw-dev.key) \
  claude -n fw-dev --mcp-config ~/.config/labctl/claude-mcp.json
```

`-n` names the session (prompt box, `/resume` list, terminal title).
Other `claude` options and a prompt go **before** `--mcp-config`: it takes
several files, so a prompt after it is read as a config file name.

To make this a single word, add a shell function to `~/.bashrc`:

```bash
# Start Claude Code as labctl agent NAME: labagent NAME [claude options...]
labagent() {
    local name=$1 key=~/.config/labctl/agents/$1.key
    if [[ ! $name =~ ^[A-Za-z][A-Za-z0-9_-]*$ ]]; then
        echo "usage: labagent NAME [claude options]" >&2
        return 1
    elif [ ! -s "$key" ]; then
        echo "labagent: no key for agent '$name' at $key" >&2
        return 1
    fi
    shift
    # "$@" first: --mcp-config would take a trailing prompt as a file.
    LABCTL_API_KEY=$(cat "$key") claude -n "$name" "$@" \
        --mcp-config ~/.config/labctl/claude-mcp.json
}
```

```bash
labagent fw-dev                          # interactive
labagent fw-dev "Check the serial console on pi-5-1"   # with a first prompt
labagent ci-boottest -p "Run a 10x boot test on pi-5-1" \
    --allowedTools mcp__labctl                          # scripted
```

With `-p` (print mode) nobody can answer permission prompts, so allow the
labctl tools up front: `--allowedTools mcp__labctl` allows all of them.
Destructive tools still need their two-step confirmation, unless the
server turned it off (`mcp.confirm_destructive: false`) or exempted the
tool (`mcp.confirm_exempt`).

Notes:

- If `LABCTL_API_KEY` is unset, Claude Code sends the text
  `${LABCTL_API_KEY}` literally and the server refuses it (401); the
  function above refuses to start instead.
- If the directory also has a `labctl` server from `claude mcp add`
  (Method A), the `--mcp-config` one is used. Avoid mixing the two
  anyway, or add `--strict-mcp-config`, which ignores every MCP server
  not in `--mcp-config` (other servers you use included).
- The key is in the session's environment, so commands the agent runs can
  see it (`echo $LABCTL_API_KEY`). See the isolation note under
  [How it works](#how-it-works).

## Agent instructions

Identity only helps if agents claim boards. Put rules like these in the
agent's `CLAUDE.md`:

```markdown
## Lab hardware (labctl)
- Use the labctl MCP tools for all lab hardware. Never run the `labctl`
  CLI for power, serial, SDWire or flashing: it doesn't see your MCP
  claims, and never pass `--override-claim`.
- Before touching a board, `claim_sbc` it (with a short `reason`; leave
  `agent_name` unset so the claim shows your labctl user). If it
  is claimed by someone else, wait or call `request_sbc_release`.
- `release_sbc` as soon as you are done; `renew_sbc_claim` for long runs.
- Never call `force_release_sbc` unless I ask.
- Destructive tools return `confirmation_required` first: check the plan,
  then call again with the same arguments plus `confirm_token`. Never
  call one "to see what happens": if confirmation is turned off, the
  first call acts.
```

## Checking an agent's identity

Ask the agent to claim a spare board, then:

```bash
labctl -c /etc/labctl/config.yaml activity tail
#   ... mcp-http:<process>:fw-dev  claim  test-board ...
labctl -c /etc/labctl/config.yaml claims list
#   test-board  held by fw-dev (...)
```

(These open the service's database: being in the `labctl` group is
enough only if the database file and its directory are group-writable;
otherwise prefix them with `sudo -u labctl`.)

The name after the last `:` in the activity log comes from the key: if it
is another agent's name, the two share a key. `claims list` shows the
claim's `agent_name`: the username, unless some session with that key
passed `agent_name`, which then applies to all of that user's later
claims until the server restarts.

## Revoking or rotating a key

Changes to `auth.users` take effect in `labctl-mcp` on the next request,
without a restart; restart `labctl-web` too if it is running, since it
reads keys only at startup.

- **Revoke:** first have the agent release its claims (`labctl -c
  /etc/labctl/config.yaml claims list`): without a key it can't call
  `release_sbc`, and its boards stay blocked until the claims expire or
  are force-released. Then delete the user's entry from `auth.users`
  (`sudoedit`), delete `~/.config/labctl/agents/NAME.key`, and for
  Method A, `claude mcp remove labctl -s local` in that directory.
- **Rotate:** delete the key file, rerun Step 1 with the same name, put
  the new `api_key` in the config in place of the old one, and for
  Method A `claude mcp remove labctl -s local` and add it again. Claims
  belong to the username, not the key, so they survive; sessions still
  running with the old key get 401 until you restart them.
